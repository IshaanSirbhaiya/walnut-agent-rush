# Decisions log

Product and engineering decisions, each with its reason. IDs are stable because code and other docs cite them; a
missing ID is a decision that was only about planning and has been removed.

| # | Decision | Why |
|---|---|---|
| D-02 | Brand **Walnut DataBridge**; "Internal Brain" is the ask product inside it | One product name for the whole platform, and a separate name for the part people ask questions in |
| D-03 | The stack runs locally on one machine by default, with no hosted dependency; a generic Docker deployment for any Docker host is in `deploy/docker/` | Reliability: nothing outside the machine has to be up for the product to work |
| D-04 | One Next.js app (`internal_brain_web`) with a User/Developer switch; small diagrams with React Flow 11.11.4 + seeded d3-force (the knowledge graph moved to Sigma, D-18) | React Flow is already proven in the repo and fits one-hop subgraphs of ≤150 nodes; the repo design law says React Flow first, Sigma only above ~1–2k visible nodes |
| D-05 | Developer views that show other people's requests or org-wide numbers need `compliance_officer`; everyone else gets their own trace and their own graph, and a lock card that explains why | Least privilege is the product; aggregate denial counts would hint at hidden content |
| D-06 | `/ib/trace` shows the asker only what they were already shown: stages, timings, model, grounding, released and cited documents, and the sealed record hashes. Never the considered set or Gate-2 reasons | Rule 4 (one response shape) |
| D-07 | Rejected suggestions: "Searched N (K allowed, J hidden)" and "something exists but is hidden" in User mode | They break restricted ≡ non-existent, the core security property |
| D-08 | No token streaming: the grounding check must finish before any text is shown. The UI shows a staged status line while waiting, then reveals the verified answer | Unverified text must never reach the screen |
| D-09 | Developer mode embeds the Walnut engine (entity graph, time slider, provenance, ontology) through a new `/api/walnut` proxy to the gateway on :8300, restyled; the old :3300 app is left as it is | The whole graph and engine belong in Developer mode; reusing the real engine is faster and honest |
| D-10 | Demo history is seeded through the real pipeline and labelled as replay in the ledger and the UI | Analytics needs data; never fake numbers |
| D-11 | Design: Linear/Vercel restraint with Palantir density; dark default; Inter bundled; no gradients or neon | The repo's frontend design law and the design research |
| D-12 | Languages: English + 简体中文 for User mode and navigation | Singapore users; cheap to do well |
| D-16 | `/ib/trace` = public-safe receipt (live re-authorised citations, coarse stages, no seq, ledgered); ms waterfalls only in the compliance journey | Review finding: titles of uncited released docs and ms timings were side channels |
| D-17 | "View as" = two independent, separately signed-in graphs side by side; no greyed or locked placeholders | Review finding: placeholders reveal that hidden objects exist |
| D-18 | Knowledge graph on Sigma 3.0.3 + graphology (WebGL); React Flow only for small diagrams | ~1,230 nodes is above React Flow's comfort zone |
| D-19 | The tamper check runs on a copy of the live ledger via a compliance endpoint; the real chain is never edited | Later requests (for example MCP tool calls) write real records after the tamper check, so the real chain must stay intact |
| D-20 | SSE stage events replace the elapsed-time status line; text still only after grounding | A time-driven status line would show progress that had not happened |
| D-21 | `/api/walnut` proxy: closed GET-only allowlist, no ask or ingest paths, gated to jdoe or compliance sessions | Review finding: the engine graph is jdoe's view and its /brain/query bypasses the gates |
| D-22 | No Malay or Tamil machine translations; English + 简体中文 only | Bad translations hurt more than they help |
| D-24 | Live growth ("watch the brain grow"), "Add a document" (Slack note and file upload), the "not in the brain yet" absence check and the engine-snapshot refresh are **demonstration features behind a toggle**: the server mounts their routes only with `IB_DEMO_FEATURES=1` (set only by `scripts/demo_up.sh`, ignored when `IB_DEPLOYED=1`; off, each route is the unknown-route 404), and the web shows them only when `/ib/status` says so AND the viewer turned "Demo features" on in Settings or the Presenter is armed, each labelled "Demo". Live growth polls a permission-filtered change feed (not SSE), and a note is posted as the signed-in person | They are demonstration features, not product surfaces for normal users; off by default keeps the attack surface of a normal run unchanged. Polling reuses the principal dependency, the write-ahead ledger and the proxy slots; SSE cannot send the Compare slot header. Posting as the token's subject keeps "identity only from the token" |
| D-25 | **Deliverables from an answer** (table, chart, analysis; `.csv` and `.pptx` export) are a product feature behind a **kill switch**, not a demo-only toggle: `IB_DELIVERABLES=1`, off by default in code, on in `scripts/demo_up.sh` and `scripts/run_local_demo.sh`; the routes stay mounted and, off, answer the not-found 404 and record nothing; turning it off needs an IB restart. Built on Act's action context (only the asker's own answer and the cited documents they can open now). **Table and Chart work without a model** (copied from a CSV-shaped block or a numeric column of a cited source, through the same checks as model output). **Model kinds say "Needs the model"** when no model is configured (Analysis is not available without a model; Summary is not built). Every value is checked by our code against its own cited source line (number span, label binding, unit and currency), never against the answer's sentences | The feature writes nothing to any source, so a demo-only switch would undersell it, but new model-facing code needs an off switch (review finding). Table and Chart from the sources need no model, so they are honest offline; nothing pretends to be model-written. A second model checking the first is not proof; a deterministic check is |
| D-26 | The three live-growth steps are added to the presenter script only when demo features are on **and** the tab opted in with `?grow=1` (`?grow=0` turns it off). The default script is its 11 steps (00–10) | Review finding: with demo features on, Space landed on an 18.6 s graph step that then would not advance |
| D-27 | Pin `opencv-python-headless==5.0.0.93` and `XlsxWriter==3.2.9` in `requirements-lock.txt` | The convert package imports `cv2` at load, so a fresh install refused PDF/PPTX uploads (13 failures). python-pptx's chart export needs XlsxWriter |
| D-28 | A model-written Act draft sentence is kept only if ≥ 80 % of its content words appear in the facts it is tagged with; otherwise the draft falls back to the cited sentences | Review finding: the answer wall (one shared word) let a customer reply add promises or tipping-off reasons. A draft is customer-facing, so it gets the stricter floor |
| D-29 | The Deliverables "Summary" kind is not built; Slides (.pptx) is, for ready tables and charts, with no model | Offline, a summary would only repeat the cited sentences (Act's draft already does that); a model summary needs a configured model |
| D-30 | The compliance MCP server is never written into a shared MCP client user config (`--compliance-user-config` writes it alone), and MCP tool output frames source text as data | Review finding: a planted sentence could steer an agent holding three identities into the compliance server |
| D-31 | Act state for rate limits, proposals and unknown Jira outcomes stays in memory (lost on restart) | A one-process service; persistence would add a store to secure. Documented in backend_v1 v3.1 |
| D-33 | Once `P` has started the presenter script, `Esc` closes an open sheet or dialog but never hides the HUD; `H` hides it. The grow step's Add sheet is presenter-owned, so `Space` drives the walk-up | Review finding: `Esc` hid the HUD mid-script, and the open sheet swallowed `Space` |
| D-34 | **Upload folder picker by name, writable folders only.** The upload tab lists Drive folders by name from `GET /sim/upload-folders`: ONLY the folders the signed-in person may upload into now, each checked live with the upload's own write check, as `[{id, path}]` sorted by path; anyone else gets `[]`. Mounted under exactly the switches of `/sim/upload-file`; 10 per minute; ledgered as `graph.viewed` `mode="upload_folders"` (counts only). An ancestor folder's name shows only to people who can open it. The typed folder ID stays as a collapsed "Advanced" fallback, only when the list is empty or fails | A typed id needed a hint that named a real folder, which told everyone it exists (review finding, rule 4); a name list is what a person can use. Listing only writable folders, checked live, adds no new knowledge: each one would accept the upload anyway. The upload re-checks WRITE regardless of what the sheet sent |
| D-36 | **The User and Developer tours are separate.** Each mode offers its own tour the first time a signed-in person is in it (User: `/`, `/compare`, `/history`, `/settings`; Developer: `/dev/*`). Neither tour starts, resumes or offers the other: the User tour ends in User mode with no "switch to Developer" hand-over, and a tour left open closes when the page moves to the other mode. The header button starts the current mode's tour. "Not now" on one mode's offer leaves the other mode's offer | One chained tour pulled a User-mode visitor into Developer pages they had not chosen, and resumed a half-finished tour after a mode switch. Two self-contained tours match the two audiences (business user or engineer) and keep the just-in-time view steps in the User tour only |
| D-37 | **Make this a page** (just-in-time views) is built on A2UI v0.9 (`@a2ui/react` 0.13.0, Apache-2.0) with our own component catalog, as a new route `POST /ib/views` beside deliverables (same kill switch), not as a new deliverable kind. Offline, rules read the request's words to pick and order blocks; a model, when configured, may propose layout and content through a closed schema checked by the deliverables checks. The server compiles A2UI itself; the tree binds paths, the data model holds the checked values | A2UI separates layout from data, so the model never writes a value; its React renderer supports our React 18 (json-render needs React 19 and Tailwind 4; Thesys C1 is a hosted generator whose content would skip our checks). A separate route leaves deliverables byte-for-byte unchanged. Rules make it work with no model |
| D-38 | The Ask view gets a clean light look and a **canvas**: a page opens beside the chat (the chat moves left), not under the answer; the action rows become one Next steps panel. Scoped to Ask (`.ask-x`) and to light mode without high contrast | Design brief: simple and clean, light mode first, the generated view shown on the right as a canvas. Scoping keeps every other page, dark mode and the projector theme exactly as reviewed |
| D-39 | **The optional AI model composes the pages** when one is configured: it decides page or chat per answer and lays the page out freely (blocks, order, headings, tone, accent), never the content: every value is checked against its source by our code. With no model, the rules compose the page (D-37). Spend caps and rate limits apply (D-42) | The product should choose when to open a page and build what was asked ("a table in black", "each person and what they did"), not fixed layouts. A page needs more than an answer's few citations, so it may read up to 12 more of the asker's own documents on the subject, each through both gates |
| D-40 | When a model is configured, **the model writes the chat answers** through the provider-neutral adapter: the passages are the gated ones, the grounding wall runs on the text and any failure is the quoted answer. A follow-up or a long question is first rewritten into one standalone search question by the model (`POST /ib/rewrite`, the person's own words only), and the chat shows "Searched for". Model chain: the configured AI model, then its fallbacks (`IB_MODEL_FALLBACKS`), then the deterministic extractive answer | The quoted (no model) answer was weak for long and follow-up questions ("What was said in Slack? (…the whole earlier question…)" returned the same answer). Same spend caps as the pages |
| D-41 | **Vendor SDKs only in `packages/harness`.** `scripts/check_vendor_imports.py` fails on a vendor-SDK import anywhere else. The optional model uses one provider-neutral HTTPS adapter for a chat-completions-style JSON endpoint (`IB_MODEL_URL`, `IB_MODEL_NAME`, `IB_MODEL_KEY`), so no vendor SDK is needed; an earlier temporary two-file exception for an optional model client is retired with it | `packages/**` is never modified, and a single neutral adapter keeps the product free of any vendor dependency |
| D-42 | **Model guardrails that a demo reset cannot refresh.** One guard (`databridge_ib/model_guard.py`) for every model call (answers, pages, rewrites): a persistent spend ledger outside the demo state (`databridge/var/model_guard/spend.json`, git-ignored, or `IB_MODEL_GUARD_DIR`; append-style, each call recorded with UTC time, estimated cost, a persona hash and its kind), a total cap (`IB_MODEL_CAP_USD`, default US$11), a daily cap per UTC day (`IB_MODEL_DAILY_CAP_USD`, default US$5), a service-wide rate (`IB_MODEL_RPM`, 20 a minute) and a per-person rate (`IB_MODEL_USER_RPM`, 6 a minute). Caps are read at start-up only; no API or screen changes a cap or the spend. A missing ledger counts as zero only in a new guard directory; a corrupt, unreadable or unwritable one stops every call and is never overwritten. Any limit hit means no call: answers are quoted, pages use the rules, rewrites return the question as asked, with the usual neutral labels and a counts-only ledger row. `demo_up.sh --fresh`, `demo_day.ps1 reset -Fresh` and `/sim/reset` never touch the guard directory (the scripts refuse a state that is, holds or sits in it). The numbers ("Model budget": spent and total cap, today and daily cap, calls) are shown on the preflight board and in `/ib/status` to admin and compliance only | A configured model can spend real money on a shared service; a fresh reset must not reset the budget, and a damaged ledger must stop calls rather than restart the count at zero. Model cost depends on the model you configure. Tests: `tests/test_model_guard.py` |
| D-43 | **Approved customer wording is quoted, never sent to a model to be re-worded.** When the deterministic quoted answer over the RELEASED passages (after Gate 1 and the live Gate 2) cites approved scripts or templates and nothing else (the document title says "approved … script" or "approved … template"), the model is not called: the quote is served with `model.reason_code: "quoted_approved_script"` and the label "Approved wording, quoted exactly". The rule keys on the passages the quote **cites**, not on everything released: the cited set is exactly what would be served and what a model would re-word, and up to 14 passages are released per ask, so keying on all of them would almost never fire. Both sets are functions of the released passages only, so a document the asker cannot open can never change the decision | Account-restriction call workflow test: Amy's approved script was sometimes paraphrased by the model and sometimes rejected by the wall; the wall does not enforce verbatim wording. Quoting is exact, the same every time and needs no model call. Tests: `tests/test_quoted_script_skip.py` (incl. a paired world with a restricted "approved" script), `tests/test_story1_fixes.py::test_a_hidden_non_script_document_does_not_change_the_skip`; the leak eval checks every skip independently (`evals/internal_brain/capture.py`) |
| D-44 | **Account-restriction call fixes, all generic.** (1) The answer prompt asks the model to state every key status fact the passages give (a filing and whether it was made, a decision and its outcome, each count), with the grounding wall unchanged (`narrate.STATUS_FACTS_RULE`, prompt `ib-prompt-2026-10-30.1`). (2) A quoted answer after a model try says why: `model.reason_code` `model_rejected_evidence` or `model_unavailable`; no code when no model is configured; each has its own EN and 简体中文 label, never a provider name. (3) The page-or-chat prompt sends case and status overviews built from two or more documents to a page (`views/composer.CASE_OVERVIEW_RULE`); "Open as page" stays available. (4) HTTP client loggers run at WARNING, so `ib.log` names no endpoint host. (5) The model answer call waits at most `IB_MODEL_ANSWER_TIMEOUT_S` (default 12 s, no retry), then the quote is served | Findings of the model-on workflow test: Rachel's answer left out the STR filing and at times the device link, the "no model" label showed after a model try, the log named the endpoint host, and the case page did not open by itself. None of these rules names a case, document or domain (rule 6). Tests: `tests/test_story1_fixes.py`, `tests/e2e/model-label.spec.ts` |
